# Резервное копирование базы и восстановление

Работа по задаче #90. Дата: 29.09.2026.

Приёмка задачи требует не скрипт создания архива, а **доказанное
восстановление с протоколом сравнения.** Поэтому главный артефакт здесь -
не расписание, а проверка `scripts/check_backup_restore.py`, которая
поднимает отдельный экземпляр PostgreSQL, восстанавливает в него дамп
и сверяет данные с исходными.

## Протокол проверки, снятый 29.09

```
1. Кладу в рабочую базу помеченную строку
2. Снимаю дамп рабочим скриптом
   backup: готово sirena112-20260929T181908Z.dump, 36 КБ
3. Поднимаю чистый экземпляр PostgreSQL
4. Восстанавливаю дамп
5. Сверяю восстановленное с исходным
```

| Таблица | Было | Стало | Итог |
| --- | --- | --- | --- |
| scenarios | 4 | 4 | совпало |
| training_sessions | 2 | 2 | совпало |
| session_reports | 2 | 2 | совпало |
| service_assignments | 28 | 28 | совпало |
| auth_accounts | 0 | 0 | совпало |
| auth_audit | 0 | 0 | совпало |
| flyway_schema_history | 4 | 4 | совпало |

Плюс: состав и контрольные суммы миграций совпали, кодировка UTF8 совпала,
помеченная строка на месте (значит дамп свежий, а не старый файл со стенда),
кириллица в данных цела.

Учётные записи и журнал аудита в замере пустые, потому что на стенде
авторизация не включалась. Сверка их всё равно покрывает: расхождение
в количестве было бы поймано.

## Как запустить

```bash
# рабочая база и Core должны быть поднятыми
python scripts/check_backup_restore.py
```

Код возврата 0 - восстановление подтверждено, 1 - нет, причина печатается.

**Рабочую базу проверка не портит.** Она добавляет одну строку в свою
таблицу `backup_check` и восстанавливает в отдельный контейнер, который
в конце удаляет. Ничего не удаляет и ничего не перезаписывает.

## Расписание

Сервис `postgres-backup` в `compose.yaml`. Первая копия снимается сразу
после старта, дальше раз в сутки: иначе до следующего дня администратор
не знает, работает ли backup вообще.

Расписание сделано простым циклом, а не cron. В автономном контуре меньше
движущихся частей, а состояние всё равно лежит файлом.

| Переменная | По умолчанию | Что задаёт |
| --- | --- | --- |
| `BACKUP_INTERVAL_SECONDS` | 86400 | как часто снимать |
| `BACKUP_KEEP` | 7 | сколько копий хранить |
| `BACKUP_MAX_MB` | 2048 | предел на каталог |

## Где лежит и кто видит

Том `postgres-backups`, внутри контейнера `/backups`. Каталог закрыт правами
`700`, файлы `600`: дамп содержит учебные данные целиком.

Состояние последнего запуска - `/backups/last-backup.json`:

```json
{
  "result": "ok",
  "message": "дамп создан, 36 КБ",
  "file": "sirena112-20260929T182001Z.dump",
  "finishedAt": "2026-09-29T18:20:02Z",
  "database": "sirena112",
  "keep": 7,
  "note": "Записи звонков сюда не входят: это только база."
}
```

**Сигнал сбоя не теряется.** При неудаче в тот же файл пишется
`"result": "error"` с текстом от `pg_dump`, а код возврата ненулевой -
цикл расписания пишет об этом в журнал контейнера. Проверено: с неверным
именем базы состояние становится `error`, недописанный файл удаляется.

Файл разбирается машинно в обоих случаях. Сначала он ломался: текст ошибки
`pg_dump` содержит кавычки, и JSON после сбоя не читался вовсе. Экранирование
добавлено, оба пути проверены.

## Ротация

Две границы, чтобы диск на стенде не кончился молча:

- по количеству - хранится `BACKUP_KEEP` последних копий;
- по объёму - если каталог всё равно больше `BACKUP_MAX_MB`, самые старые
  копии удаляются, пока он не уложится.

## Восстановление

```bash
RESTORE_DB=sirena112_restore sh scripts/restore_postgres.sh /backups/файл.dump
```

Скрипт **отказывается** писать в базу, чьё имя не содержит `test`, `restore`
или `check`: восстановление пересоздаёт базу и стирает данные, и сделать это
по ошибке нельзя. Для рабочей базы нужен явный `RESTORE_FORCE=yes`.

`pg_restore` запускается с `--exit-on-error`: частично восстановленная база
хуже явной ошибки.

## Чего этот backup не покрывает

Задача #90 прямо требует это оговорить, чтобы не возникло ложного чувства
сохранности занятия.

**Записи звонков не входят в дамп базы.** Они лежат файлами в томе
`voice-recordings`, в базе хранятся только метаданные. Если том потерян,
восстановление базы вернёт историю занятий и отчёты, но не звук. Хранение
записей - 7 дней по настройке из #87, и отдельной копии у них нет.

**Шифрование дампа не реализовано.** В образе `postgres:16-alpine` нет
`openssl`, а доставлять его в автономный контур - отдельное решение.
Сейчас защита - только права на каталог. Шифрование хранимых данных
относится к #89 и там не сделано, так что заявлять его нельзя.

**Администратор видит состояние файлом, а не в интерфейсе.** Рабочее место
администратора из #135 этот файл пока не показывает. Подключить - небольшая
работа, но она не сделана, и делать вид, что сигнал виден в интерфейсе,
неправильно.

## Найдено по дороге

Первый прогон проверки **уложил Core.** Скрипт создал свою таблицу
`backup_check` в базе, где Flyway ещё не применял миграции, и Core
отказался стартовать: «Found non-empty schema but no schema history table».

Ошибка была в проверке, не в приложении, и это ровно то, чего от проверки
ждать нельзя. Теперь скрипт сначала убеждается, что история миграций есть,
и отказывается работать с базой, к которой Core не подключался.

Само поведение Flyway при этом правильное: он не мигрирует поверх чужих
объектов. Но стоит помнить, что любой инструмент, который лезет в схему
раньше Core, ломает старт приложения.
