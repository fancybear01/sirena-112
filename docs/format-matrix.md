# Матрица форматов: что заявлено и что проверено

Проверка по задаче #98. Дата: 29.09.2026.

Каждая строка получена прогоном `scripts/check_formats.py` на поднятом стеке,
а не чтением кода. Формат не объявляется поддержанным на основании того, что
он упомянут в ТЗ.

## Как повторить

```bash
docker compose -f compose.card.yaml up --build --detach --wait ai core
python scripts/smoke_card_1050602.py --core http://127.0.0.1:8080 --expect-ai

python scripts/check_formats.py \
  --core http://127.0.0.1:8080 \
  --core-container sirena-card-core-1 \
  --postgres sirena-full-postgres-1
```

Код возврата 0 - расхождений нет, 1 - есть, и они печатаются списком.

Отдельно про `--core-container`: импорт сценариев разрешён только с локального
адреса, а запрос снаружи приходит с адреса шлюза Docker и получает 403.
Поэтому проверки импорта идут изнутри контейнера, где адрес настоящий loopback.

Тестовых файлов в репозитории для этого не нужно: скрипт берёт сценарий из
самого Core, меняет идентификатор и заголовок и импортирует обратно. Своей
копии каталога он не хранит - по тому же правилу, по которому её нет у AI.

## Что проверено по каждому формату

**JSON API.** Отчёт занятия и аналитическая сводка забираются у Core,
разбираются как UTF-8, содержат не-ASCII символы. Схема API описана в
`contracts/openapi.yaml` и проходит валидатор в CI.

**JSON сценариев.** Все четыре примера из `contracts/examples` проходят
`contracts/scenario.schema.json` (JSON Schema draft 2020-12).

Круговорот: сценарий выгружен из Core, получил новый идентификатор и заголовок
с кириллицей и «ё», импортирован, прочитан обратно. **Ни одно поле не
изменилось, кириллица цела.**

Отказы импорта проверены тремя способами, все три дают код и сообщение:

| Что подсунули | Код | Сообщение |
| --- | --- | --- |
| чужая версия классификатора | `CATALOG_VERSION` | Ожидается версия 046-2024-11-15 |
| сценарий без рубрики | `SCHEMA` | `$: required property 'rubric' not found` |
| уже существующий идентификатор | `DUPLICATE_ID` | id ... уже существует |

Ограничения импорта: пакет `{"scenarios": [...]}`, от 1 до 25 элементов,
до 2 МБ. Сообщение об этом приходит текстом, если формат не тот.

**SQL, PostgreSQL 16.15.** Кодировка сервера и клиента UTF8, длина русской
строки считается верно. Схема ведётся миграциями Flyway V1-V4, данные лежат
в `JSONB`, время в `TIMESTAMPTZ`. Сохранение и восстановление после
перезапуска проверяется в CI шагом `core / postgres-recovery`.

**XLSX.** Файлы отчёта и сводки открываются `openpyxl`, содержат по одному
листу и 32 и 14 строк соответственно. Тип содержимого верный.

**PDF.** Версия 1.4, текст извлекается `pypdf`. Шрифт берётся из
`CORE_EXPORT_FONT_PATH` либо из системных путей, а в образе Core установлен
`fonts-dejavu-core` - то есть на пустой машине без шрифта выгрузка не
упадёт молча, а скажет, чего не хватает.

**WAV.** Речь, которую отдаёт AI: PCM16, моно, 16 кГц - как требует контракт
с Media. Проверяется не только заголовок: доля ненулевых отсчётов 98-99%,
то есть это настоящий звук, а не тишина нужной длины.

**Фикстуры PCM и RTP** у Media лежат в `services/media/tests/voicefixture/`
с манифестом, где у каждого файла размер, длительность и sha256. Целостность
там проверяется хешем.

**WAV записи занятия.** Появилась в #87, который влили во время этой проверки.
Формат: PCM16 little-endian, 8 кГц, стерео. Левая дорожка - обучающийся,
правая - то, что AI реально отправил в RTP. На вход подаётся µ-law по одному
байту на отсчёт, запись декодирует его в PCM16.

Проверено не по документации, а прогоном того же кода, что работает в бою:
собрала запись через `recording.Recorder` и разобрала своим валидатором.

| Что проверяла | Итог |
| --- | --- |
| структура файла | 2 канала, 16 бит, 8000 Гц, читается стандартной библиотекой |
| длительность | кратна 20 мс, как обещано |
| дорожки не перепутаны | левая и правая различаются |
| декодирование µ-law | совпало с независимым декодером Python побайтово: -5372 и 716 |

Ограничения записи: не дольше 15 минут (около 28,8 МБ стерео), хранение
7 дней, очередь 100 кадров, при переполнении запись считается неудачной и
RTP не задерживается. Файл пишется как `.wav.part` и становится `.wav`
атомарным переименованием только после записи заголовка - то есть
недописанная запись не может притвориться готовой.

Раздаётся только через Core с авторизацией, преподавателю своей группы и
администратору. Media сырой WAV наружу не отдаёт, в PostgreSQL звук не
кладётся.

Отдельно стоит помнить про две частоты: контракт AI с Media - 16 кГц моно,
а запись - 8 кГц стерео. Это не расхождение, а разные задачи: в разговоре
важна разборчивость, в записи - разделение сторон.

Своей ошибки не скрою: первый прогон дал «целостность нарушена», потому что
я подала в `Frame` отсчёты PCM16, а он ждёт µ-law. Дефект был в моём вызове,
а не в записи.

## Открытые дефекты, найденные проверкой

**1. Выгрузки XLSX и PDF на английском и беднее, чем JSON.**

В отчёте по занятию через API есть текст каждого критерия и рекомендации:

```json
{"code": "GREETING", "passed": true, "points": 0.0,
 "message": "Представился и назвал службу"}
"recommendations": ["Критерий «GREETING» автоматически не проверяется, оцените его вручную."]
```

В XLSX от этого не остаётся ничего - только `Criterion GREETING passed`,
`Criterion GREETING points`, `Criterion GREETING max`. Ни текста критерия,
ни рекомендаций, ни ошибок. Заголовки листа: `Training report`, `Metric`,
`Value`, `Session ID`.

Почему это важно: выгрузка - это то, что преподаватель забирает на разбор
с курсантом. Без формулировок критериев она превращается в таблицу чисел.
И система русская, а выгрузка английская.

**2. Сообщение о нарушении схемы приходит на английском.**

`$: required property 'rubric' not found` - это текст от библиотеки
валидации, отданный пользователю как есть. Остальные два отказа импорта
написаны по-русски, этот выбивается.

**3. Сортировка базы не русская.**

Сортировка `en_US.utf8`. Русские слова упорядочиваются не по алфавиту:

```
Яблоко < дом < если < ёлка
```

Заглавная буква идёт раньше всех строчных, а «ё» уезжает в конец вместо
места после «е». По русскому алфавиту порядок был бы другим. Это заметно
в любом списке курсантов, сценариев или занятий, отсортированном базой.

**4. Неверный метод даёт 500 вместо 405.**

`GET /api/teacher/sessions` отвечает `500 INTERNAL_ERROR`. Такого метода нет,
есть только `POST`. Ошибка клиента выглядит как поломка сервера, и искать
её будут не там. Список занятий, если он нужен, берётся из
`/api/teacher/history`.

## Чего нет и почему

**CSV.** В ТЗ упомянут наравне с XLSX и PDF. В коде нет ни одного места,
где CSV пишется или читается. Это не блокер и не чужая зависимость - просто
не сделано. Для выгрузки в Excel XLSX уже есть, так что вопрос в том, нужен
ли CSV формально.

**MP3.** В ТЗ упомянут рядом с WAV. Запись занятия появилась в #87, но пишется
она в WAV, а не в MP3. Перекодирования в системе нет, и внешних препятствий
тоже нет - просто не сделано. Практически WAV задачу закрывает: файл
открывается любым плеером, а стерео нужно для разбора сторон, которое при
сжатии в MP3 сохранилось бы, но добавило бы зависимость от кодека.

**Legacy XML.** ТЗ допускает его как необязательный. В системе он не
используется: конфигурация Asterisk ведётся в собственном формате `.conf`,
обмен идёт JSON. Отсутствие отмечено осознанно.

**Шифрование хранимых данных.** Задача #89 открыта. Проверять нечего.

**Сжатие.** В передаче и хранении рабочих данных не применяется. Единственное
место, где есть архив, - `images.tar` в offline-поставке, и он собирается
средствами Docker. Целостность после восстановления проверяется командой
`doctor` из `docs/offline-full-stack.md`, а не этой матрицей.

## Вывод

Все форматы, которые в системе реально есть, читаются, пишутся и
проверяются - это подтверждено прогоном, а не чтением кода.

Два формата из ТЗ отсутствуют, и оба не из-за чужих зависимостей: CSV не
сделан вовсе, MP3 не сделан - запись занятия пишется в WAV.

Четыре дефекта найдены и описаны выше; самый заметный для пользователя -
английские выгрузки без текста критериев.

превратилась в проверенную.
