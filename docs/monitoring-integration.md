# Интеграция с мониторингом и системой доступа заказчика

Работа по задаче #95. Дата: 29.09.2026.

Интеграция построена на открытых стандартах и не привязана к конкретному
продукту заказчика: метрики отдаются в формате Prometheus, статус - в JSON,
отправка во внешнюю систему - по HTTP с Bearer-токеном. Адаптер заменяемый и
покрыт тестами против поддельного сервера, поэтому подключение к стенду
заказчика сводится к настройке адреса и токена.

## Мониторинг: что можно забирать

Два способа, оба на сервисе `monitor`, порт 8099, привязан к 127.0.0.1.

### Сбор метрик, основной путь

```
GET /metrics
Content-Type: text/plain; version=0.0.4; charset=utf-8
```

Текстовый формат Prometheus выбран потому, что его читают все
распространённые системы: Prometheus, VictoriaMetrics, Zabbix через
HTTP-агент. Так интеграция не привязана к одному закрытому продукту -
заказчику достаточно настроить сбор с этого адреса.

```
sirena_up 1
sirena_component_up{component="postgres"} 1
sirena_component_up{component="asterisk"} 1
sirena_component_up{component="ai"} 1
sirena_component_up{component="media"} 1
sirena_component_up{component="core"} 1
sirena_component_up{component="web"} 1
sirena_speech_real 1
```

| Метрика | Что значит |
| --- | --- |
| `sirena_up` | стенд готов целиком: 1 готов, 0 нет |
| `sirena_component_up` | готовность компонента, метка `component` |
| `sirena_speech_real` | работают настоящие речевые модели, а не подмены |

Последняя метрика нужна отдельно: подмена речи снаружи выглядит как
работающий сервис, и на демонстрации это первое, что стоит проверить.

**Названия метрик и метки - часть контракта.** На них настраивают
оповещения, и переименование ломает чужие настройки молча. Поэтому имена
закреплены тестом: `infra/monitor/test_monitor.py`.

### Подробный статус в JSON

```
GET /status
GET /ready    # 503, если стенд не готов - для проверок готовности
GET /health   # живость самого монитора
```

`/status` отдаёт то же в JSON, с причиной отказа по каждому компоненту.
Это удобнее человеку и годится системам, которые умеют разбирать JSON.

### Отправка статуса наружу

Если система заказчика не умеет забирать сама, статус можно отправить ей.

```
POST /push
```

| Переменная | Что задаёт |
| --- | --- |
| `MONITOR_PUSH_URL` | адрес приёмника; пусто - отправка выключена |
| `MONITOR_PUSH_TOKEN` | уходит как `Authorization: Bearer ...` |
| `MONITOR_PUSH_TIMEOUT` | таймаут, по умолчанию 5 секунд |

Уходит тот же JSON, что на `/status`, с заголовком `X-Request-Id`. Тот же
идентификатор возвращается в ответе, чтобы сбой интеграции можно было
сопоставить с записью в журнале.

Коды ответа различаются намеренно:

| Ситуация | Код | Тело |
| --- | --- | --- |
| отправка выключена | 200 | `delivered: false, reason: push_disabled` |
| доставлено | 200 | `delivered: true` |
| система заказчика отказала | 502 | `delivered: false` с её кодом |

Выключенная отправка - это состояние настройки, а не сбой шлюза, поэтому
не 502. По 502 администратор понимает, что дело не у нас.

**Отправка выключена по умолчанию.** Автономный контур - основной режим,
и он не должен зависеть от внешней системы. Монитор сам наружу по
расписанию не стучится: отправку инициирует администратор или планировщик.

## Что проверено

`infra/monitor/test_monitor.py`, 14 проверок против поддельного сервера:

| Что | Итог |
| --- | --- |
| формат метрик и разбираемость | проверено |
| названия метрик закреплены | проверено |
| упавший компонент отличается от рабочего | проверено |
| подмена речи видна в метрике | проверено |
| доставка статуса, заголовки, тело | проверено |
| токен уходит в заголовке | проверено |
| отказ внешней системы: 502, не падение | проверено |
| недоступная система не роняет монитор | проверено |
| токен не утекает в результат и журнал | проверено |
| наружу уходит тот же статус, что на /status | проверено |

Живой прогон: метрики отдаются с верным типом содержимого, старые методы
`/status`, `/ready`, `/health` не сломаны.

Нашлось по дороге: токен с кириллицей давал ошибку кодека вместо внятного
сообщения - заголовки HTTP не переносят символы вне latin-1. Теперь
возвращается понятная причина, и сам токен в неё не попадает.

## Система доступа: контракт интеграции

Контракт подключения к локальной системе доступа заказчика. Учётные записи,
группы и роли уже ведутся в Core, поэтому адаптер только синхронизирует их
с внешним источником.

Что нужно от системы заказчика:

| Что | Зачем | Формат |
| --- | --- | --- |
| учётные записи | вход преподавателей и обучающихся | JSON или XML, по их протоколу |
| группы | назначение заданий группе | то же |
| роли | разделение прав ADMIN, TEACHER, STUDENT | то же |

Ограничения, которые надо соблюсти при реализации:

- **Персональные данные посторонних в учебный контур не импортируются**
  без обоснования. Нужны только идентификатор, отображаемое имя, группа
  и роль. Ни телефонов, ни адресов, ни должностей.
- Доступ к методу импорта закрывается ролью ADMIN и идёт по TLS.
- Сбои пишутся в журнал с `requestId`, как это сделано в отправке статуса.
- Адаптер заменяемый: конкретный продукт в коде не называется.

Сейчас учётные записи ведутся своими средствами: таблица `auth_accounts`
и роли из #82. Автономный режим от системы заказчика не зависит и работать
без неё продолжает - это требование приёмки соблюдено.

## Режимы работы

- **Автономный** - основной: учётные записи в `auth_accounts`, мониторинг
  на 127.0.0.1, отправка наружу выключена.
- **Интеграция с заказчиком** - сбор `/metrics` их системой либо
  `POST /push` с `MONITOR_PUSH_URL` и `MONITOR_PUSH_TOKEN`.
