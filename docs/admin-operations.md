# Администрирование локального комплекса

Страница `/admin` показывает readiness Core, AI, Media, PostgreSQL и Asterisk,
нагрузку CPU/RAM/диска, последние ошибки, безопасные параметры и аудит
управляющих команд. Данные обновляются каждые 5 секунд и вручную кнопкой
«Обновить состояние».

## Запуск

Обычный запуск автоматически поднимает локальный helper до контейнеров:

```powershell
.\scripts\stack.ps1 start
```

```bash
bash scripts/stack.sh start
```

Рабочее место требует включённого RBAC: перед production-сборкой задайте в
локальном `.env` `CORE_AUTH_ENABLED=true` и `VITE_AUTH_MODE=secure`. Скрипты и
UI намеренно не изменяют эти конфигурационные значения автоматически.

Helper слушает только `127.0.0.1:8100`. Если комплекс уже запущен старой
командой, helper можно запустить отдельно:

```powershell
python .\scripts\admin_helper.py
```

После входа с ролью `ADMIN` откройте <http://localhost:5173/admin>. Cookie
сессии проверяется helper через `GET /api/auth/me`; учитель, обучающийся и
анонимный запрос получают отказ.

## Безопасность команд

- Browser может передать только действие `start`, `stop`, `restart` или
  `update` и только компонент из фиксированного allowlist.
- Helper не использует shell-строку: он формирует массив аргументов для
  `scripts/stack.ps1` или `scripts/stack.sh`.
- Перед каждой командой UI показывает подтверждение, а helper повторно
  проверяет ADMIN-сессию, одноразовый CSRF-токен и loopback Origin.
- Чтобы администратор мог снова запустить остановленный Core, helper держит в
  памяти только хеш недавно проверенной сессии, логин и роль не более 15 минут. Ответ
  Core 401/403 никогда не заменяется кэшем; кэш используется лишь при
  недоступности Core и пропадает при перезапуске helper.
- Пакетное обновление разрешено только для всего комплекса и использует
  локальный `offline-bundle/images.tar`; путь из браузера не принимается.
- Аудит без паролей, токенов и вывода процессов хранится вне проекта:
  `%LOCALAPPDATA%\sirena-112\admin-actions.jsonl` на Windows или
  `$XDG_STATE_HOME/sirena-112/admin-actions.jsonl` на Linux.
- API helper не содержит операций оценки, редактирования сценария или
  занятия. Сбой helper/мониторинга не меняет состояние карточного режима.

## Конфигурация и секреты

В браузер передаются только разрешённые несекретные значения: bind-адрес и
порты SIP/RTP, имя/пользователь/порт БД, лимиты записи и уровень логирования.
Пароли и service tokens не читаются в API, не возвращаются клиенту и не
записываются в browser storage. Меняйте их вручную в `.env` на сервере и после
этого выполняйте restart.

## Восстановление

1. Если `/admin` сообщает, что helper недоступен, запустите
   `python scripts/admin_helper.py` и проверьте <http://127.0.0.1:8100/health>.
2. Если Core недоступен для проверки прав, выполните
   `.\scripts\stack.ps1 status` и `.\scripts\stack.ps1 logs` (на Linux —
   соответствующие команды `stack.sh`).
3. При сбое отдельного компонента используйте его кнопку restart. Если это не
   помогло, выполните restart всего комплекса; том PostgreSQL сохраняется.
4. Перед восстановлением БД остановите активные занятия. Создание и возврат
   дампа выполняйте по [`docs/postgres-core.md`](postgres-core.md).
5. После восстановления проверьте, что все компоненты имеют статус «Работает»,
   затем запустите `stack.ps1 smoke` или `stack.sh smoke`.

Не выполняйте `down --volumes`: эта команда удаляет данные PostgreSQL и не
используется админкой.
