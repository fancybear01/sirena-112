# Восстановление сессии и границы отказоустойчивости

Проверка задачи #92. Цель — восстановить доступ к сохранённой карточной сессии
не более чем за 30 секунд после краткого разрыва сети, падения процесса Core или
переключения на второй Core. Все свойства ниже подтверждены прогоном.

## Что включено в штатный стек

- У сервисов с долгим жизненным циклом задана ограниченная политика
  `restart: on-failure:5`. После исчерпания попыток контейнер остаётся упавшим,
  чтобы журнал и причина не скрывались бесконечным циклом.
- Health/readiness проверяются для PostgreSQL, Core, AI, Media, Asterisk, Web и
  monitor. `monitor` после трёх неудачных проверок публикует alert
  `recovery=FAILED`; admin-helper передаёт его в красный блок «Значимые ошибки».
- Web переподключает WebSocket с последним обработанным `afterEventId`. Core
  читает из PostgreSQL только хвост после курсора, а при неизвестном курсоре
  делает безопасный полный replay. Web всегда дедуплицирует по `eventId`.

Команда оператора `docker compose stop` считается намеренной и не вызывает
автоперезапуск. Скрипт завершает PID 1 изнутри контейнера и отдельно фиксирует,
сработал ли автоматический restart либо процесс завершился штатно и потребовал
явного запуска. Политика `on-failure:5` проверяется для каждого сервиса.

## Два Core для приёмочного теста

`compose.resilience.yaml` добавляет `core-2` с той же PostgreSQL и
`core-gateway`. В этом профиле Web направляет API и WebSocket через gateway.
Gateway использует привязку по IP, поэтому обычные запросы одного клиента идут
на один Core, а после отказа узла следующий reconnect попадает на оставшийся.

Запуск (тест намеренно останавливает и аварийно завершает контейнеры):

```bash
AI_REQUIRE_REAL_SPEECH=false docker compose \
  -f compose.yaml -f compose.resilience.yaml \
  up --build --detach --wait monitor
python scripts/check_resilience.py --network-outage-seconds 30
```

Скрипт не удаляет volumes и в `finally` возвращает сервисы в запущенное
состояние. Он выполняет последовательность:

1. создаёт сессию, запускает её и сохраняет ревизию карточки;
2. отсоединяет Web от Compose-сети ровно на 30 секунд;
3. восстанавливает сеть, продолжает ту же карточку и сохраняет результат;
4. по очереди оставляет только `core-2` и только `core`, сверяя сессию, отчёт и
   уникальность `eventId`;
5. перезапускает оба Core и повторно читает тот же результат;
6. завершает Core, AI, Media и PostgreSQL по отдельности, проверяет политику
   restart, фактический способ восстановления, readiness и время не более 30 с;
7. unit-тестом доводит счётчик monitor до порога и проверяет передачу alert о
   неудавшемся восстановлении в admin-helper.

В CI это job `demo / resilience`. При ошибке job печатает журналы всех
компонентов, а затем удаляет только свой временный CI-volume.

## Владение состоянием и деградация

| Отказ | Что сохраняется | Граница деградации |
| --- | --- | --- |
| Core | Сессия, карточка, события и отчёт в PostgreSQL | Gateway переключает новый HTTP/WebSocket-запрос на второй Core; активное соединение переподключается |
| AI | Сохранённая карточка и уже готовый отчёт | Новая AI-операция временно недоступна или использует предусмотренный fallback Core; `aiSessionId` и голосовой контекст в памяти AI теряются |
| Media | Бизнес-состояние Core и PostgreSQL | Активный SIP/RTP-звонок и временное состояние Media теряются; карточный режим продолжает работать |
| PostgreSQL | Данные именованного volume | Пока БД недоступна, оба Core не готовы и запись/чтение сессии невозможны; это единая точка отказа |

Core остаётся единственным владельцем бизнес-состояния. Оба Core используют
уникальные ограничения PostgreSQL для `eventId`, поэтому повтор одного события
не создаёт вторую запись или вторую оценку. Media и AI не читают основную БД.

## Архитектурные решения

- Отказоустойчивость процессов обеспечивается на одном Docker-host: этого
  достаточно для изолированного учебного контура.
- Событие, принятое другим Core, дочитывается из PostgreSQL при reconnect по
  `afterEventId` - отдельный брокер live-событий не нужен.
- `ip_hash` удерживает клиента на одном узле; учебная сессия и её данные при
  переключении узла сохраняются.
- Alert о неудавшемся восстановлении виден в monitor и в рабочем месте
  администратора.

## Результат локальной проверки

Локальный полный прогон 29.09.2026 завершился `PASS` для одной и той же сессии
`c66446d5-7e0d-49f6-937a-304461cd5e96`; в PostgreSQL осталось 27 уникальных
событий без повторов.

| Проверка | Время | Способ восстановления |
| --- | ---: | --- |
| Разрыв сети | 30,250 с | заданная длительность теста |
| Reconnect Web | 0,016 с | автоматический |
| Переключение на `core-2` | 0,000 с | gateway |
| Возврат на `core` | 2,187 с | gateway |
| Restart двух Core | 12,422 с | Compose |
| Падение Core | 11,812 с | автоматический `on-failure` |
| Завершение AI | 16,563 с | штатный exit, явный start |
| Завершение Media | 8,422 с | штатный exit, явный start |
| Завершение PostgreSQL | 6,875 с | штатный exit, явный start |

AI, Media и PostgreSQL обработали тестовый сигнал как штатное завершение,
поэтому политика `on-failure` ожидаемо не перезапустила их. Скрипт не выдаёт
это за автоматическое восстановление: он явно запускает контейнеры и отражает
режим в JSON. При ненулевом завершении действует ограниченная политика
`on-failure:5`; автоматическое восстановление фактически подтверждено для Core.
Каждое восстановление уложилось в требуемые 30 секунд.
