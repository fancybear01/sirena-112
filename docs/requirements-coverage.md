## Чего нет, и это надо сказать прямо

### Численные показатели ТЗ измерены наполовину

| Показатель | Норматив | Состояние |
| --- | --- | --- |
| отклик API | p95 ≤ 2 с | **0.14 с**, измерено |
| 20 учебных занятий одновременно | бюджет паузы 1.2 с | **0.67 с**, измерено |
| VoIP one-way latency | ≤ 150 мс | **не измерено ни разу** |
| 100 одновременных пользователей | - | **не измерено** |
| запись в базу | ≥ 100 операций/с | **не измерено** |
| формирование отчёта | ≤ 30 с | **не измерено** |

Задача #91 закрыта, но в репозитории есть только замеры AI. Ни скрипта
нагрузки на Core, ни протокола по VoIP, ни документа с числами по базе и
отчётам нет: поиск по всему репозиторию находит упоминание 150 мс только
в тексте ТЗ и в моём документе, где прямо написано, что я эту величину
не измеряла.

Отдельная оговорка к измеренному. Мои числа сняты локально на macOS.
В поставочном образе те же двадцать занятий дают 3.86 с вместо 0.67 -
вшестеро хуже. Похоже на накладные расходы Docker Desktop, но это
предположение: проверить можно только на целевом Linux-сервере. До такой
проверки измеренные числа - верхняя граница, а не обещание.

### Backup базы отсутствует полностью

Задача #90 открыта. В репозитории нет ни скрипта создания архива, ни
восстановления, ни расписания. Требование ТЗ о ежедневном backup и
проверенном восстановлении не выполнено ничем.

### TLS отсутствует, аудит частичный

Задача #89 открыта. TLS нет ни для браузера, ни для внутренних каналов.

Аудит есть, но частичный: таблица `auth_audit` (миграция V2) пишет входы и
действия над учётными записями с полями actor, action, subject, outcome,
requestId. Требований #89 она не покрывает: изменения сценариев, оценок и
материалов, доступ к записям, хранение не менее шести месяцев и контроль
целостности журнала.

Модели угроз и проверки требований 149-ФЗ и 152-ФЗ как артефакта нет.

### Мониторинг и интеграция с системой доступа заказчика

Задача #95 открыта. Actuator подключён, но наружу отдаёт только `health`
и `info` - метрик нет. Адаптеров к локальной системе доступа и мониторинга
нет, контрактных тестов на поддельном сервере нет.

Это единственная строка с честной внешней блокировкой: заказчик не
предоставил протоколы и стенд. Но описание точек интеграции и заменяемый
адаптер с тестами сделать можно и без стенда - этого тоже нет.

### Списка библиотек и лицензий нет

Требование #96. В репозитории нет ни одного файла с перечнем зависимостей
и их лицензий. Для сдачи это обязательный пункт раздела «Требования к
решению», и он не выполнен.

Отдельно важно, потому что по лицензиям у нас уже находились ошибки:
`piper-tts` под MIT только до версии 1.2.0, дальше GPL-3.0-or-later, а у
голоса `ru_RU-irina` лицензия обучающих данных - Unknown. Подробности в
`docs/voice-shipping-stack.md`. Без сводного списка такие вещи теряются.

### Массовые вызовы и восстановление сессии

Задачи #80 и #92 открыты. Массовое поступление учебных вызовов не
реализовано, восстановление сессии за 30 секунд при обрыве сети не

### Адаптивная сложность

Задача #78 открыта. Причина не в коде: в каталоге `contracts/examples`
четыре сценария и **все уровня BASIC**. Задача требует по одному сценарию
на каждый из трёх уровней и прямо запрещает переименовать BASIC без
методического обоснования. Пока в каталоге не появятся сценарии остальных
уровней, проверить логику выбора уровня нечем.

## Трассируемость: у 18 закрытых задач нет машинной связи с кодом

Задачи закрыты, но связать их с влитым изменением автоматически нельзя:
ни `Closes #N` в PR, ни номера в сообщении коммита.

Оговорка о методе: номер задачи в истории пишут по-разному - `(#107)`,
`issue 9`, `67 issue`. Сначала мой скрипт ловил не все варианты и объявил
#67 непрослеженным, хотя он в истории есть. Поправлено, список ниже
уже точный.

```
#1 #2 #3 #4 #10 #11 #12 #14 #51 #52 #55 #61 #63 #65 #69 #70 #71 #96
```

Это **не значит, что работа не сделана**. По части из них я вижу код своими
глазами: голосовой поток из #52 лежит в `services/ai/app/web/voice_routes.py`,
интерфейс из #61 и #63 - в `apps/web`. Но для приёмки, которая требует
доказательство на каждую строку, отсутствие трассировки - это дыра: проверяющий
не может пройти от требования к изменению.

Особенно это важно для #65 и #96 - релиз-кандидата и комплекта материалов.
Обе закрыты, обе требуют артефактов: SHA, скрины, резервное видео, документ,
презентация, четыре работающие ссылки. Ни один из этих артефактов в
репозитории не находится. Если они есть вне репозитория, ссылки надо
приложить к #64; если их нет - закрытие было преждевременным.

## Что нельзя заявлять при сдаче

Список для материалов #64 и #96. Каждый пункт проверяем, поэтому
преувеличение обойдётся дороже умолчания.

1. Не заявлять соответствие численным показателям ТЗ целиком. Измерены
   отклик API и двадцать одновременных занятий. VoIP-задержка, сто
   пользователей, скорость записи в базу и время формирования отчёта не
   измерены.
2. Не заявлять защищённость данных. TLS нет, аудит частичный, шифрования
   хранимых данных нет.
3. Не заявлять надёжность. Ежедневного backup и проверенного восстановления
   нет.
4. Не заявлять интеграцию с системой доступа и мониторинга заказчика.
   Отмечать как внешнюю блокировку, потому что стенда действительно нет.
5. Не заявлять поддержку CSV и MP3. CSV не сделан, запись занятия пишется
   в WAV.
6. Не заявлять адаптивную сложность: в каталоге только уровень BASIC.
7. Про голос говорить точно: живой разговор подтверждён на поставочном
   образе, но задержки под нагрузкой в контейнере вшестеро хуже локальных
   и на целевом сервере не проверялись.

## Что можно заявлять смело

Всё это проверено прогоном, а не словами.

1. Карточный режим целиком: признаки, вопросы, адрес, пострадавшие,
   вычисление происшествия и служб по официальному классификатору,
   объяснимая оценка с разбором по критериям.
2. Живой голосовой разговор с AI-абонентом на локальных моделях, без
   интернета и без видеокарты. Распознавание дословное, ответ за полсекунды.
3. Запись занятия в WAV со разделением сторон по каналам, целостность
   проверена независимым декодером.
4. Хранение в PostgreSQL с восстановлением состояния после перезапуска -
   проверяется в CI на каждом изменении.
5. Выгрузка отчётов в XLSX и PDF, импорт и экспорт сценариев с проверкой
   схемы и версии классификатора.
6. Проверяемая оценка текста карточки с измеренной точностью и честной
   маркировкой того, чему нельзя верить без преподавателя.
7. Автономный offline-контур с диагностикой.

## Как повторить сверку

```bash
python scripts/check_coverage.py
```

Скрипт берёт состояние задач из GitHub, сопоставляет с историей `main` и
печатает то же, что в сводке выше. Он не заменяет проверку по существу,
но ловит расхождение между «задача закрыта» и «изменение влито».
