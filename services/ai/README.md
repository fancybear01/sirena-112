# AI Service

Python-сервис с локальными моделями.

Ответственность:

- генерация сценариев и эталонов;
- моделирование поведения абонента;
- классификация происшествия;
- анализ свободного текста и транскрипта;
- рекомендации по результатам занятия;
- STT/TTS либо адаптеры к локальным речевым процессам.

Сервис получает контекст через Kotlin Core и не имеет прямого доступа к
основной схеме PostgreSQL.

## Голосовой режим

Core создаёт AI-сессию и передаёт разрешённый контекст сценария, Go Media
подключается по `aiSessionId` к бинарному WebSocket и гоняет PCM. AI отвечает
за абонента: распознаёт фрагмент речи, выбирает реплику и озвучивает её.
Управление Asterisk остаётся в Go, оценка занятия - отдельный запрос после.

| Метод | Путь | Назначение |
| --- | --- | --- |
| POST | `/ai/voice/sessions` | создать сессию под звонок, получить `aiSessionId` |
| DELETE | `/ai/voice/sessions/{aiSessionId}` | освободить сессию |
| WS | `/internal/v1/voice/{aiSessionId}?sessionId=...` | поток PCM и сообщений |

Формат и порядок сообщений заданы `contracts/media-ai.md`.

### Речь подключается моделями, а не встроена

Пара моделей выбрана замерами из `docs/ai-benchmark.md`: Vosk для распознавания
и Piper для синтеза, оба на процессоре и с разрешительными лицензиями.
Подключаются переменными окружения:

```bash
AI_STT=vosk   AI_STT_MODEL=/path/vosk-model-small-ru-0.22
AI_TTS=piper  AI_TTS_MODEL=/path/ru_RU-irina-medium.onnx
```

Модели не скачиваются автоматически и не нужны для тестов: в CI работают
детерминированные подмены. Состояние моделей на демо-стенде и что делать,
если их нет: `docs/voice-readiness.md`.

Piper отдаёт звук на частоте своего голоса (у ru_RU-irina это 22050 Гц),
адаптер пересчитывает его к 16000 - как требует контракт с Media.

**Заглушка не выдаётся за распознанную речь.** Если моделей нет, поток отвечает
ошибкой `speech.unavailable` с объяснением, а не придуманным текстом. Если
вместо моделей работают подмены, каждый транскрипт помечен `simulated: true`,
и это же видно в ответе на создание сессии.

### Что ограничено

Фрагмент речи не длиннее 30 секунд, к одной сессии подключается один поток,
число одновременных сессий ограничено. Сырой звук в логи не пишется - только
его длительность.

### Проверить локально

```bash
.venv/bin/python scripts/smoke_voice.py
```

Скрипт поднимает приложение в своём процессе, создаёт сессию, прогоняет
сгенерированный PCM и печатает обмен. Телефония и модели не нужны.

## Откуда берутся данные

Своих классификационных данных сервис не хранит. Это главное правило
после перехода на официальный классификатор.

| Что | Откуда |
| --- | --- |
| сценарии | `contracts/examples/scenario-*.json` - те же файлы, что у Core |
| признаки, вопросы, названия служб | `contracts/catalog/classifier-v046-11.json` |
| состав оповещённых служб | расчёт Core, приходит в запросе на оценку |
| характер абонента и рубрика оценки | наш сервис |

Рубрика заслуживает отдельного слова. Каталог про методику обучения ничего
не знает, и импорт кладёт в сценарий заглушку с одним критерием. Поэтому
сервис дополняет рубрику до минимального набора - и при выдаче сценариев,
и при оценке сценария, пришедшего от Core. Полную рубрику преподавателя
он при этом не трогает: если все обязательные критерии на месте, считается
по ней.

Разделение простое: в каталоге лежит происшествие, у нас - методика обучения.
Классификатор не знает и не должен знать, насколько заявитель напуган и сколько
баллов стоит адрес.

Службы AI не маршрутизирует. Оператор их не выбирает: состав оповещения следует
из признаков и ответов, и считает его Core. AI только сравнивает расчёт Core
по карточке обучающегося с тем, что записано в эталоне.

На то, чтобы копия каталога не завелась снова, есть отдельные тесты:
`tests/test_no_duplicate_catalog_data.py` ищет в исходниках названия служб
и коды классификатора.

Пути можно переопределить переменными `AI_CATALOG_PATH` и `AI_SCENARIOS_PATH`.

## Как устроен AI-абонент

Реплика собирается **только** из значений эталона сценария. Обрамляющие слова
вроде "Записывайте" не содержат ни адреса, ни имени, ни обстоятельств. Поэтому
абонент физически не может сообщить того, чего нет в сценарии - не потому что
его об этом попросили, а потому что взять неоткуда.

Вопрос оператора распознаётся по ключевым словам из `question_intents.py`.
Словарь живёт в коде, а не в сценарии: набор вопросов оператора 112 задан
регламентом, он конечный и одинаковый для пожара, ДТП и запаха газа.

У абонента три шкалы - паника, доверие, терпение. Они меняются от действий
оператора: представился по регламенту - доверие растёт, задал вопрос по делу -
паника спадает, повторил уже отвеченный вопрос или спросил невпопад - терпение
убывает. На нуле терпения абонент бросает трубку и занятие проваливается.

Состояние между репликами хранит Core и присылает обратно: сервис не помнит
ничего между запросами.

Случайности нет ни в одном месте. Одинаковый разговор всегда идёт одинаково,
иначе занятие невозможно было бы разобрать с преподавателем.

## Запуск

```bash
cd services/ai
python3 -m venv .venv
.venv/bin/python -m pip install -e ".[dev]"
.venv/bin/python -m uvicorn app.main:app --port 8090
```

Документация API поднимается на `http://localhost:8090/docs`.

Тесты:

```bash
.venv/bin/python -m pytest
```

Переменные окружения: `AI_HOST`, `AI_PORT`, `AI_ENGINE`, плюс `AI_CATALOG_PATH`
и `AI_SCENARIOS_PATH` для переопределения путей к каталогу и сценариям.
Значения по умолчанию взяты из `.env.example` в корне репозитория; порт 8090
совпадает с `core.ai-base-url`, по которому Core обращается к сервису.

### Правила, на которые можно опираться

- Все поля наружу в camelCase.
- Незаполненные необязательные поля в ответ не попадают. Это требование
  `contracts/scenario.schema.json`, где для таких полей разрешён конкретный тип,
  но не `null`.
- Неизвестное поле в запросе это ошибка, а не молчаливое игнорирование.
- Ошибка приходит в том же формате, что и у Kotlin Core: `timestamp`, `status`,
  `code`, `message`, `path`, `requestId`, плюс `details` со списком полей.
- Заголовок `X-Request-ID` принимается и возвращается обратно; если его нет,
  сервис создаёт свой.
- Ответы детерминированы: одинаковый запрос даёт одинаковый результат.
  Для генерации это обеспечивается полем `seed`.

### Эталон описывает ввод оператора и результат его обработки

`groundTruth.expectedInput` - это то, что оператор должен был записать
в карточку: признаки, ответы на вопросы, адрес, пострадавшие, описание.
Остальные поля эталона вычисляемые: код классификатора, тип происшествия,
сценарий реагирования и состав служб.

Абонент знает ровно то, что лежит в `expectedInput`. Больше ему взять
неоткуда, поэтому выдумать обстоятельства он физически не может.

## Как устроена оценка

Карточка обучающегося сравнивается с эталоном по восьми критериям. Поля карточки
названы так же, как `OperatorCard` в Kotlin Core: это один и тот же объект.

Оценивается то, что оператор действительно делает: выбирает признаки, отвечает
на обязательные вопросы, собирает адрес, фиксирует пострадавших и описывает
обстоятельства. Тип происшествия и службы он не вводит, поэтому сравнивается
не введённая строка, а код классификатора, вычисленный Core.

**Ошибки разделены по источнику.** `OPERATOR` - обучающийся сделал не то.
`GROUND_TRUTH` - вопрос к данным: разошлись версии каталога, не передан расчёт
Core, в эталоне нет служб. Вторые видны в отчёте, но зачёт не закрывают
и в вину обучающемуся не ставятся.

Отчёт всегда несёт `sessionId`, `scenarioId` и `classifierVersion` - по ним
видно, по какому эталону считали.

Что важно знать:

**Частичное выполнение считается честно.** Выбрал три службы из четырёх - это
три четверти баллов, а не ноль. Лишняя служба тоже ошибка: её зря поднимут
по тревоге.

**Адрес сравнивается по значимым частям.** "д. 21" и "дом 21" это одно и то же,
город можно не писать, "к1" понимается как корпус 1. Зато в объяснении видно,
чего именно не хватило: "не указано: корпус 1, подъезд 3". Оценка, которая
придирается к сокращениям, быстро теряет доверие.

**Признаки происшествия важнее итогового типа.** В АРМ-112 оператор выбирает
признаки, а тип и список служб следуют из их комбинации. Поэтому сравниваются
идентификаторы признаков из каталога, а в объяснении показываются их названия:
"не выбрано: дым".

**Критерии про общение проверяются по транскрипту** тем же словарём вопросов,
который управляет поведением абонента в диалоге. Один разбор реплик работает
в обе стороны.

**В карточном режиме звонка нет**, и критерии про разговор просто не участвуют
в распределении баллов: наказывать за непредставление там, где оператор
физически не говорил, нельзя.

**Штрафы отделены от критериев.** Критерии показывают качество работы, штрафы -
нарушение жёстких нормативов. Поэтому норматив времени живёт только в штрафах:
одна и та же ошибка не должна наказываться дважды.

### Инварианты отчёта об оценке

1. Сумма `maxPoints` по критериям равна `maxScore`.
2. `totalScore` равен сумме `earnedPoints` минус сумма штрафов и не ниже нуля.
3. Каждый критерий не в статусе `PASSED` имеет запись в `errors` с кодом и
   понятным объяснением.

Эти правила проверяются тестами и должны сохраниться после подключения
настоящей модели оценки.

## Структура

```text
app/
  config.py            настройки и выбор движка
  schemas/             контракты запросов и ответов
  catalog.py           справочники классификатора, только для названий
  engines/             сценарии каталога, поведение абонента, оценка
  web/                 маршруты, middleware, обработка ошибок
tests/                 проверка контракта, инвариантов и ошибок
```

Для запуска нужен Python 3.10 или новее: зависимости проверки контрактов
на 3.9 уже не ставятся.
