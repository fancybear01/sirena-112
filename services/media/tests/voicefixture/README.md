# Фиксированные кадры и fake AI WebSocket

## Что хотели сделать

До подключения настоящего AI получить автоматическую проверку формата аудио
и обмена по WebSocket, которую можно повторить без прослушивания звонка.
Ожидаемый путь: RTP μ-law → PCM16 → fake AI WebSocket → ответный PCM16 → μ-law.
Протокол сообщений берётся из
[`contracts/media-ai.md`](../../../../contracts/media-ai.md).

Исходные требования:

1. Подготовить короткие фиксированные кадры RTP G.711 μ-law 8 кГц / 20 мс
   и PCM16 mono 16 кГц / 20 мс; записать размеры, длительность, порядок байтов
   и границы кадров.
2. Проверить преобразование в обе стороны, включая тишину и несколько
   последовательных пакетов, по ожидаемым байтам, а не на слух.
3. Проверить на fake AI порядок `stream.start` → binary audio → `input.flush`
   → ответный PCM → `stream.stop`.
4. Проверить ограничение очереди и закрытие соединения после одного обрыва,
   чтобы медленный AI не задерживал обработку телефонного потока.
5. Зафиксировать ожидания для согласования с Полиной, команду теста и ссылку
   на PR. По последующему указанию владельца ветки отправка сообщения и
   создание PR не выполняются; описание остаётся здесь.

## Что сделано и как принимать

| Требование | Где проверяется / текущая граница |
|---|---|
| Фиксированные байты и параметры кадров | `testdata/`, `manifest.json`, таблица ниже |
| Тишина и три кадра туда-обратно | `TestFixturesRoundTrip` в `fixtures_test.go` |
| Полный аудио-оборот через fake WS | `TestFakeAITwoTurns` в `websocket_test.go` |
| Переполнение очереди и один обрыв | Тесты рабочих `internal/adapters/ai` и `asterisk/rtp` |
| Завершение соединения и worker | WS-тест ожидает завершения клиента и сервера с timeout |
| Отсутствие блокировок рабочего ARI/RTP-моста | Рабочие адаптеры проверяются также в `internal/adapters/asterisk/ari` |
| Открытый/слитый PR | Не выполнено: изменения оставлены локально по указанию владельца |

Локальная проверка стенда успешна, если команда ниже завершилась с `PASS`
для обоих тестов и без сообщений race detector. Рабочий AI-мост проверяется полным набором тестов Media. Исходная приёмка также требует PR до перехода
к реальному AI; этот пункт остаётся за владельцем ветки.

## Как запустить

Запуск из корня репозитория (нужен Go 1.26.5):

```bash
cd services/media
go test -race -v ./tests/voicefixture
```

Реальные AI, Asterisk, модели и softphone не нужны. Тест использует временный
loopback HTTP/WebSocket сервер. Сеть вне компьютера не используется.

## Зафиксированные ожидания

| Данные | Частота | Отсчёты на кадр | Размер кадра | Длительность |
|---|---|---|---|---|
| RTP G.711 μ-law / PCMU, PT=0 | 8 кГц | 160 | 12 байт header + 160 payload = 172 | 20 мс |
| PCM16 signed LE mono | 16 кГц | 320 | 640 байт, без header | 20 мс |

Файлы `testdata/00`, `01`, `02` идут в этом порядке: 3 кадра / 60 мс,
516 байт RTP и 1920 байт PCM. Один `.rtp` — один UDP datagram; один `.pcm` —
одно binary WebSocket message. Объединение или изменение порядка кадров
в этом fixture-профиле считается ошибкой. Сам общий контракт допускает другие
размеры аудиофреймов; здесь проверяется рекомендованный профиль 20 мс.

RTP header: network byte order (big-endian), V=2, PT=0, без padding/extension,
SSRC `0x12345678`, sequence `65535, 0, 1`, timestamp `0, 160, 320`.
Переход sequence через ноль намеренный. Timestamp измеряется в отсчётах 8 кГц.

PCM: signed int16, little-endian. +988 = `dc 03`, -988 = `24 fc`, ноль = `00 00`.
Каждый исходный отсчёт μ-law представлен двумя PCM16k отсчётами:

- `00`: тишина, μ-law `ff`, PCM нули;
- `01`: 80 отсчётов μ-law `ce` (+988), затем 80 `4e` (-988);
- `02`: 40 отсчётов `4e`, 40 `ff`, затем 80 `ce`.

В μ-law есть два представления нуля; fixtures используют положительный ноль
`ff`, чтобы обратное преобразование имело однозначные байты.
Размеры, длительность и SHA-256 каждого файла зафиксированы в `manifest.json`.
Ожидаемые PCM-файлы созданы из явно заданных значений 0/+988/-988, а не из
результатов Go-конвертера во время теста. Тест сравнивает направление RTP→PCM
и обратное направление с фиксированными файлами, а не только друг с другом.

## Что доказывают тесты

- `TestFixturesRoundTrip`: исходные golden-файлы, μ-law codec, signed LE PCM,
  границы кадров, тишина и RTP sequence rollover. Здесь сохранён тестовый
  эталон удвоения частоты, чтобы не менять опубликованные golden-байты.
- `TestFakeAITwoTurns`: **рабочий клиент** `internal/adapters/ai` передаёт
  три PCM-кадра и `input.flush` в каждом из двух ходов. Fake AI не отвечает
  на отдельные кадры; после flush присылает `transcript.final`, JSON
  `response.started`, binary PCM, `response.completed`, `caller.state_changed`.
  Затем проверяется `stream.stop` и завершение клиента/сервера.

Рабочий фильтрующий FIR-ресемплер проверяется отдельно в `internal/adapters/audio`:
он имеет групповую задержку и не обязан побайтно совпадать с исходным
zero-order-hold эталоном. Проверяются тишина, непрерывность между пакетами,
ограниченная ошибка кругового преобразования и подавление aliasing.

Очереди, disconnect, отмена, pacing и повторные звонки проверяются на рабочих
адаптерах в `internal/adapters/ai`, `internal/adapters/asterisk/rtp` и `ari`.
Команда полного набора:

```bash
go test -race ./...
```

Тест с текущим Python AI и команды softphone smoke описаны в
[AI bridge](../../docs/ai-websocket.md). PR не создаётся: изменения остаются
локально по указанию владельца ветки.
