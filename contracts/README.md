# Контракты Sirena-112

## Версия 0.2

openapi.yaml и scenario.schema.json описывают один контракт карточки.
Версия 0.2.0 — намеренно breaking change относительно прототипа 0.1.0:

- клиент передаёт только OperatorCardInput;
- Core возвращает OperatorCard.calculation;
- classifierCode, incidentType, ЕКП-35, сценарий реагирования и службы не
  принимаются от Web как достоверные данные;
- идентификаторы признаков и служб стабильны, а их отображаемые названия —
  только представление.

Пока API остаётся в pre-release 0.x, несовместимое изменение допускается
только при одновременном изменении версии контракта, примера и contract-теста.
После выпуска 1.0 несовместимые изменения получают отдельный путь API
/api/v{major} и сохраняют предыдущий путь до согласованного срока миграции.

## Граница ответственности

Web -> OperatorCardInput -> Core -> CardCalculation -> Web / AI

- **Web** выбирает признаки, ответы, адрес и сведения со слов заявителя.
- **Core** применяет классификатор и routing rules.
- **AI** получает версию классификатора и вычисленную ground truth; он не
  хранит отдельный список ожидаемых служб.
- **Media** не читает классификатор и не обращается к PostgreSQL.

## Эталон

examples/scenario-1050602.json — проверяемый сценарий для комбинации
«жилой дом → мусоропровод → дым». Он фиксирует:

- classifierCode = 1050602;
- итоговый тип задымление: мусоропровод;
- ЕКП-35 пожар: мусоропровод;
- сценарий реагирования 1_9;
- основную службу МЧС.

Файл валидируется тестом services/ai/tests/test_contract_examples.py.
Импортёр задачи #32 станет единственным источником production-каталога; пример
не заменяет исходный классификатор.
