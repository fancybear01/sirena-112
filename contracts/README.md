# Контракты Sirena-112

## Версия 0.3

openapi.yaml и scenario.schema.json описывают один контракт карточки.
Версия 0.2.0 отделила ввод оператора от вычислений относительно прототипа 0.1.0:

- клиент передаёт только OperatorCardInput;
- Core возвращает OperatorCard.calculation;
- classifierCode, incidentType, ЕКП-35, сценарий реагирования и службы не
  принимаются от Web как достоверные данные;
- идентификаторы признаков и служб стабильны, а их отображаемые названия —
  только представление.

Пока API остаётся в pre-release 0.x, несовместимое изменение допускается
только при одновременном изменении версии контракта, примера и contract-теста.
После выпуска 1.0 несовместимые изменения получают отдельный путь API
/api/v{major} и сохраняют предыдущий путь до согласованного срока миграции.

## Граница ответственности

Web -> OperatorCardInput -> Core -> CardCalculation -> Web / AI

- **Web** выбирает признаки, ответы, адрес и сведения со слов заявителя.
- **Core** применяет классификатор и routing rules.
- **AI** получает версию классификатора и вычисленную ground truth; он не
  хранит отдельный список ожидаемых служб.
- **Media** не читает классификатор и не обращается к PostgreSQL.

examples/scenario-1050602.json — проверяемый сценарий для комбинации
«жилой дом → мусоропровод → дым». Он фиксирует:

- итоговый тип задымление: мусоропровод;
- ЕКП-35 пожар: мусоропровод;
- сценарий реагирования 1_9;
- основную службу МЧС.

Файл валидируется тестом services/ai/tests/test_contract_examples.py.
## Каталог классификатора

`classifier.schema.json` описывает исходный нормализованный каталог отдельно от
учебного сценария: у строки XLSX ещё нет persona, адреса, ответов оператора или
готового списка требуемых служб. `catalog/classifier-v046-11.json` содержит все
1281 записи, условия колонок, справочники признаков, вопросов и служб.
Импорт и семантика описаны в `../tools/classifier-import/README.md`.

Версия API 0.3.0 меняет `mainService` на `mainServices: ServiceRef[]`:
в источнике бывают ноль, одна и несколько главных служб. `ekp35IncidentType`
и `responseScenarioCode` допускают null; `responseScenarioStatus` различает
`CODE`, `MISSING`, `EXPLICIT_NONE`, `SOURCE_LABEL`. Пустой `requiredServices`
допустим по форме, но не означает, что неполная маршрутизация подтверждена.
Неизвестные условия/конфликты должны препятствовать публикации полного эталона.
Это несовместимое изменение pre-release контракта; #33/#34/#35 используют 0.3.

Четыре `examples/scenario-*.json` генерируются из каталога. Учебный адрес, набор
ответов и rubric — синтетические fixtures, не исходные данные заказчика.
Идентификаторы признаков в старом примере 1050602 заменены на ID каталога.
Полный список служб в примерах вычисляется по колонкам, не копируется из
`mainServices`: главная служба и список адресатов имеют разную семантику.
